# Plan: Separate alert "source" identity from "alert agent" dispatch identity,
# plus a "triggered by" line for a process acting on behalf of an agent/manual action

## Context

Operator report: "regarding manual agent name in alerts... if it is a process, the source
should be process name. now, presently, I am showing it as manual, instead of process name."
Then, correcting an initial narrow fix attempt: "the source is process that generated error.
Here keeping the name as agent is not correct. there are two layers here. The source that
generated the log... the alert agent then processes it... should add its own info, and tag.
presently, everything shows as agent." Then, confirming the template direction and adding a
third dimension: "if a process is triggered by an agent or manual. how do you show that info.
there are two paths: process -> alert agent, agent/manual -> process -> alert agent... if a
process is triggered by agent or manual action, this additional info should be also displayed."
Then, on exact wording: "if the process is triggered manually, you can show source name
triggered manually. if it is by agent it could say, source name triggered by agent-name." — one
sentence, not a separate "Triggered by:" line. Then, on the tag line specifically: "the tags
should [have] action agent or manual info, process info, alert agent info, log info also" — up
to FOUR independent, separately-filterable tags, not one compound sentence-tag: (1) the action
agent or "manual" (the trigger, when known), (2) the process itself (when source is a process),
(3) the alert agent that dispatched it, (4) the log level.

Root cause, confirmed by reading the real code:
- `backend/shared/helpers/alert_utils.py:resolve_origin(agent_id, agent_name)` has exactly two
  outcomes: a real agent identity, or the literal string `"manual"`. No third state exists.
- `format_notification_header()` (same file) unconditionally prepends the literal word
  `"Agent:"` to whatever `resolve_origin()` returns — every alert's header says "Agent: ..."
  regardless of whether the real source is a background process, a raw uncategorized error, a
  genuine agent action, or a genuine manual action.
- Several real call sites paper over this by forcing a non-agent source to impersonate an agent
  via a fake `agent_id`/`agent_name` pair, purely so `resolve_origin()`'s two-state model has
  something to resolve: `event_agents.py:generic_notice_identity_extra()` maps background
  producers onto real-but-often-retired `Agent` DB rows; `MARKET_STATUS_ALERT_AGENT` and the
  close-summary cron do the identical trick. Because `MARKET_STATUS_ALERT_AGENT` is also the
  agent that dispatches its own alert, this produced the `#market_status`/`#market_status_alert`
  near-duplicate-tag bug patched narrowly (by-id) earlier today — the real fix is structural.
- `event_agents.py:_render_error()` (the `ERROR_AGENT` catch-all matching every
  `logger.error`/`logger.critical` in the app) already captures the Python logger name and
  includes it in the message BODY, but the HEADER still says "Agent: manual" because the logger
  name is never fed into origin resolution — its own docstring already calls this an "accepted,
  known imprecision."
- Separately, several PROCESS-sourced alerts (chase cancel-confirm failures, template-attach
  failures, order-poll corrections, order-cancelled) are not pure "no known cause" background
  jobs — they act on behalf of a real `AlgoOrder`, which already carries its own real
  `agent_id` (a real agent, or the manual sentinel). Today these show ONLY "Agent: {order's
  origin}" — correct but incomplete: it never says the alert actually came from the chase/
  template-attach subsystem, only who the order belonged to.

This is a refinement, not a reversal, of an earlier operator instruction ("every alert should
be generated by an agent... driven by tags", 2026-11-03) that produced today's fake-agent
pattern in the first place. The "alert agent evaluates conditions/tags and dispatches" layer
that instruction established is correct and stays — what's wrong is that a SOURCE's own
identity was forced through that same Agent-DB-row mechanism instead of being its own concept,
and a process acting on behalf of an agent/manual order was only showing the latter, not both.

**Decision confirmed by operator**: chase / template-attach / order-poll-reconcile /
order-cancelled alerts switch from today's direct `"Agent: {order's origin}"` to a single
`"Source: {process} triggered manually"` / `"Source: {process} triggered by {agent name}"`
sentence — the fuller, more precise option, not the smaller-blast-radius alternative. One
sentence, not a separate "Triggered by:" line (operator's explicit wording).

## Final template (operator-reviewed and approved)

Tag order (operator's explicit order): **action/manual, process, alert-agent, log-level** — up
to 4 independent, separately-filterable tags, never a compound sentence-tag. A tag is omitted
(not blanked/placeholder'd) when that dimension doesn't apply to this alert (no process layer,
or no known trigger). Deduped across ALL FOUR positions (generalizes today's 2-value dedup),
so two dimensions that happen to resolve to the identical value — e.g. a self-dispatching agent
that is also its own alert-agent — collapse to one tag, never repeat.

**Pure background process, no known trigger** (ticker watchdog, deploy-sync, market status,
market summary — nothing "triggered" these, they run on a timer/their own detection logic):
```
Source: Ticker watchdog
Sat 25 Apr 14:32 IST | Sat 25 Apr 05:02 EDT

Reconnected after 3 failed attempts
#ticker_watchdog #ticker_recovered_alert #info
```
(process, alert-agent, log — no action tag, nothing triggered this)

**Bare, uncategorized error** (`_render_error`, the `ERROR_AGENT` catch-all, no known trigger):
```
Source: chase (error)
Sat 25 Apr 14:32 IST | Sat 25 Apr 05:02 EDT

Broker timeout placing order for CRUDEOIL26NOVFUT
#chase #error_alert #error
```
(process, alert-agent, log — no action tag; if a future caller DOES attach a real `agent_id` to
an error-tagged record, the action tag appears for free, same as today's existing fallback)

**Process triggered by a manual order** (chase cancel-confirm failure, NEW format):
```
Source: chase triggered manually
Sat 25 Apr 14:32 IST | Sat 25 Apr 05:02 EDT

Cancel of order O1 on ZG#### could not be confirmed after attempt 2.
#manual #chase #chase_cancel_alert #warning
```
(action=manual, process=chase, alert-agent, log — all 4 present)

**Process triggered by a real agent** (chase cancel-confirm failure, NEW format):
```
Source: chase triggered by Close-on-loss
Sat 25 Apr 14:32 IST | Sat 25 Apr 05:02 EDT

Cancel of order O1 on ZG#### could not be confirmed after attempt 2.
#close_on_loss #chase #chase_cancel_alert #warning
```
(action=the real agent, process=chase, alert-agent, log — all 4 present)

**Real agent, direct action, no process layer** (rich/breach alerts — unchanged):
```
Agent: Chase close positions (#12)
Sat 25 Apr 14:32 IST | Sat 25 Apr 05:02 EDT

{breach table / message}
#chase_close_positions #chase_close_positions_alert #critical
```
(action=the agent itself — no separate process tag, there is no process layer here — alert-agent,
log)

**Genuine manual action, no process layer** (fill alerts — unchanged):
```
Agent: manual
Sat 25 Apr 14:32 IST | Sat 25 Apr 05:02 EDT

Order filled: BUY 75
Account: ZG####
BUY 75 NIFTY26OCT25000CE (NFO) @ 112.50
Product: NRML
Order id: 101
#manual #fill_alert #info
```
(action=manual, alert-agent, log — no process tag)

**No duplication, anywhere, in any case above**: the label always names the real, immediate
source once; the "triggered manually"/"triggered by {agent}" phrase is folded into that SAME
label sentence (never a separate line); the symbol/account/order-id appear exactly once in the
body (already fixed earlier today for fill alerts — this plan does not touch that, only
confirms no regression); the dual-tz IST/EDT timestamp (`timestamp_display()`/
`format_dual_tz()`, `date_time_utils.py` — already correct today, unchanged) appears exactly
once per rendered message, never restated in the body text; every tag value is distinct from
every other tag on the same line (dedup, generalized to all 4 positions, not just today's 2).
Email's subject line carrying its own copy of the timestamp is NOT a duplication in this sense
— subject and body are two separately-viewed UI surfaces (inbox list vs. opened email), each
needs its own timestamp; this plan does not change that existing, correct pattern. Email gets
the same info as a bold header block + a pill row (up to 4 pills, same dedup) instead of
hashtags — no new design needed beyond this.

**The process's own log message is the central content of the alert** (operator). The header
(source/trigger sentence + timestamp) and the trailing tags are supporting metadata ONLY —
attribution and categorization — never a restatement of what the message already says, and
never allowed to crowd out or dilute the message itself. This directly means `_render_error`'s
current generic `"RamboQuant error"` filler line AND its separate, now-redundant logger-name
body line (duplicate of the header's own process name once step 3 lands) are DROPPED, not
deferred — the message stands alone in the body, exactly as shown in the "Bare, uncategorized
error" template above.

## Schema (new, additive `extra` keys — `LogEvent.extra`/`AgentEvent.detail` are JSONB/
## schema-free per `backend/api/models.py:2726`, confirmed — zero DB migration needed)

```python
extra={
    "tags": [...], "alert_event": "...",
    "source_type": "process" | "error" | "agent" | "manual",   # NEW, optional
    "source_name": "chase",                                      # NEW, optional — the process's own name
    # UNCHANGED fields, meaning now CONDITIONAL on source_type:
    #   - source_type in ("agent","manual") or absent -> today's resolve_origin() path (unchanged)
    #   - source_type in ("process","error") -> these same fields become the OPTIONAL
    #     "who triggered this process" signal: folded into the label SENTENCE
    #     ("{name} triggered manually" / "{name} triggered by {agent}") AND emitted as its
    #     own independent tag, omitted entirely when absent (pure background job).
    "agent_id": ..., "agent_name": ...,
}
```
Reuses `resolve_origin()` for BOTH purposes (primary identity AND upstream-trigger) — no new
resolution function for the trigger case, since the two branches never overlap (a process-
sourced record's `agent_id`/`agent_name` are unused by the legacy path once `source_type` is
set). A log call that sets neither new key keeps today's exact behavior — strictly additive.
Checked against `_STANDARD_ATTRS` (`log_store.py:39`) — `source_type`/`source_name` are not
`logging.LogRecord` built-ins, no collision risk. Checked against the existing `"source"` key
already used elsewhere (`order_poll.py:234`, `orders_place.py:2674`, order-failure's own
`_classify_order_origin_label`) — using `source_type`/`source_name` (not bare `"source"`)
avoids that real collision.

`resolve_source(extra) -> tuple[str, str, str | None, str | None]` (new function,
`alert_utils.py`, next to `resolve_origin()`): returns
`(label_word, label_sentence, process_tag_or_None, action_tag_or_None)`.
  1. `source_type in ("process", "error")` and `source_name` truthy → label_word="Source";
     `action_tag` = `resolve_origin(agent_id, agent_name)` IF either is set else `None` (the
     trigger, when known); `process_tag` = `source_name` (always, when this branch fires);
     `label_sentence` = `source_name` alone when `action_tag` is `None`, else
     `f"{source_name} triggered manually"` when `action_tag == "manual"`, else
     `f"{source_name} triggered by {action_tag}"` (operator's exact wording — the LABEL stays
     one sentence; the TAGS stay four independent values, both built from the same two
     underlying resolutions — no re-derivation, no risk of the label and tags disagreeing).
  2. Otherwise → label_word="Agent", `action_tag` = `resolve_origin(agent_id, agent_name)`
     (today's exact path, unchanged) — ALSO used as `label_sentence` directly (no process layer,
     nothing to compose a sentence around); `process_tag` = `None` always.

`format_notification_header()` gains optional keyword-only `source_type`/`source_name` params,
renders `f"{label_word}: {label_sentence}"` as ONE line — no separate "Triggered by:" line.
Every existing call site passing neither new kwarg is byte-identical to today (confirmed: 16
existing renderers never pass these, all unaffected).

`_agent_tag_line()`/`_agent_pill_html()` (`event_agents.py:756`, `:799`) — rebuilt around 4
independent tag slots, in the operator's stated order: **action/manual, process, alert-agent,
log-level**. `action_tag`/`process_tag` come from `resolve_source(extra)` above (omitted
when `None` — not emitted as a blank/placeholder tag). Tag 3 (`_alert_agent_source_slug`,
"which alert agent processed it") is unchanged. Tag 4 (log level) is NEW — read from the
record's own `tags` list (`rec.get("tags")`, already populated by `log_store.py:tags_for()`'s
existing level-tagging — no new producer-side change needed, purely a consumer of data that
already exists). The existing dedup (string-equality + by-id) generalizes from 2 positions to
all 4 — a `dict.fromkeys()`-style pass over whichever of the 4 slots are non-`None`, in order,
so two dimensions that happen to resolve identically (e.g. a self-dispatching agent that is
also its own alert-agent) collapse to one tag without disturbing the stated ordering of the
ones that remain distinct.
